# DECISIONS.md

1. **Indexes.** I create seven indexes at startup, idempotently. `employees.emp_code` is unique (enforces the 409-on-duplicate guarantee and serves every employee lookup). `employees.(department, emp_code)` covers `GET /employees` filtered by department and sorted by `emp_code`, and the department-scoped analytics. `employees.joined_on` serves the `department_summary` `$match` on `joined_on <= month_end` so the headcount scan uses an index instead of a collection scan. `attendance_logs.(emp_code, date)` is unique — it is the natural key, makes `PATCH` lookups O(1), and is what makes punch-in race-safe. `attendance_logs.(date: -1, emp_code: 1)` backs `GET /attendance`'s sort+pagination so it never sorts in memory. `attendance_logs.(emp_code, punch_in)` lets punch-out find the most recent open record by index. `attendance_logs.date` serves the monthly aggregations' date range match. I considered a separate `status` index but rejected it: status is low-cardinality (5 values) and the date index already narrows the range; a status index would rarely be chosen and would cost writes.

2. **Punch-in race.** Both requests compute the same `(emp_code, attendance_date)` from the same `punched_at`. Each calls `insert_one`. The unique index on `(emp_code, date)` lets the first write succeed (201) and forces the second to raise `DuplicateKeyError`, which I catch and return as 409. There is no check-then-insert, so the outcome is determined by the index, not by timing between a find and an insert.

3. **Ties.** I use MongoDB's `$rank` (standard competition ranking: 1, 2, 2, 4), not `$denseRank`. I rank by `total_late_minutes desc` and apply `$match: {rank: {$lte: limit}}` *after* ranking. So if two employees tie at rank 2 and `limit` is 2, both are returned (the response has 3 rows). Tied rows are then ordered by `emp_code` ascending. I do not use the array position as the rank.

4. **Headcount.** `department_summary` starts from the `employees` collection filtered to `joined_on <= month_end`, then `$lookup`s each employee's logs with `preserveNullAndEmptyArrays: True`. Employees with no logs therefore still appear (their log fields are null/empty), and the final `$group` uses `$addToSet: emp_code` for headcount, so zero-log employees are counted. People who join after the month end are excluded by the initial `$match`.

5. **For 100x the data.** I would shard `attendance_logs` on `(emp_code, date)` and pre-aggregate: a daily rollup collection (`emp_code, date, department, present_value, late_minutes, overtime_minutes, work_hours`) maintained by a change-stream consumer, plus a monthly summary collection. The trend endpoint would read the daily rollup and only the `$densify`/`$setWindowFields` run on demand. I would also switch from PyMongo to Motor so a single worker can overlap I/O, and move the cross-collection `department_summary` to a denormalized view keyed by department-month.
